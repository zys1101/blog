# 从一次支付回调谈幂等性：如何面对重复通知

> 状态：写作草稿。以下是设计分析，不是已发生的生产事故或个人项目成果。发布前请补充自己的真实业务场景、实现代码与并发测试证据。本文不随博客启动自动发布。

## 1. 先澄清问题

支付平台回调可能重复、延迟或乱序到达。网络超时并不说明业务没有执行：数据库可能已经提交，但支付平台没有收到成功应答，于是再次通知。

需要保证的不是“只接收到一次请求”，而是：**同一笔已确认的支付事件，不应重复改变订单状态、增加权益或发送业务指令。**

发布前补充：接入平台、回调事件标识、验签方式、成功应答格式，以及重试协议。

## 2. 幂等键应该从业务语义出发

可以考虑 `(provider, event_id)` 唯一键，其中 `event_id` 来自支付方稳定、不可伪造的事件标识。不能仅把整个请求体做哈希：字段顺序、时间戳或签名刷新都可能让同一事件产生不同哈希。

同时还要维护订单状态机。同一订单可能有支付成功、退款、关闭等不同事件，不应只用订单 ID 把所有事件都当成重复。

## 3. 验签在前，状态变更在事务中

一个待验证的事务方案：

1. 按平台协议校验签名，核对商户、金额、币种、订单与支付流水。
2. 开启数据库事务，用唯一约束尝试登记事件。
3. 使用带前置状态条件的更新，把订单从 `pending` 改为 `paid`。
4. 在同一事务中写入后续业务的 outbox 记录。
5. 提交事务；只有确认已持久化或已成功处理，才按平台协议返回成功。

下面仅展示条件更新，不是完整支付系统代码：

```sql
UPDATE payment_order
SET status = 'paid', paid_at = CURRENT_TIMESTAMP
WHERE id = ? AND status = 'pending';
```

`affectedRows = 0` 不一定代表成功，也可能订单不存在、处于关闭状态或不允许迁移。需要读取状态，区分安全重复、业务冲突和异常，而不是一律返回成功。

## 4. 为什么不能只“先查再写”

两个并发请求都可能先查询到“未处理”，然后同时进入业务逻辑。应用层判断不是并发互斥保障。

数据库唯一约束负责竞争仲裁，条件更新负责状态前置条件，事务把事件登记、状态变化与 outbox 写入联系起来。如果发生唯一键冲突，应结束当前失败事务，再读取已有记录判断是否已经成功，而不是在失败事务中继续写入。

> 唯一键不是整个幂等方案。它只解决其中一类冲突，不能独自保证外部服务的副作用只执行一次。

## 5. 外部副作用怎么办

数据库事务不能把邮件服务或第三方发货 API 一起回滚。把外部请求直接放在事务中，还可能增加锁持有时间。

一种方案是 Transactional Outbox：事务里写待发送事件，由后台任务重试投递。消费端依旧需要幂等处理。应明确区分“数据库状态一致”和“跨系统恰好一次”；后者不能仅凭一把 Redis 锁来保证。

这只是文章讨论，个人博客本身不实现支付、队列或 outbox。

## 6. 发布前补齐验证

| 场景                     | 待验证结果                             |
| ------------------------ | -------------------------------------- |
| 同一通知顺序调用 10 次   | 订单只发生一次合法状态迁移             |
| 同一通知并发到达         | 唯一约束有效，无重复权益 / outbox 记录 |
| 提交成功后 HTTP 连接断开 | 重试被识别为已完成，可安全应答         |
| 写 outbox 前数据库异常   | 事务整体回滚，下一次通知可以重试       |
| 签名错误、金额错误       | 不登记为已成功，不改变订单状态         |
| 订单关闭后收到成功通知   | 按约定处理冲突并保留排查依据           |
| outbox 投递失败或重复    | 可重试，消费端不产生重复副作用         |

## 小结

幂等性不是某个注解或某一行 Redis 命令，而是业务语义、状态机、数据库约束和失败恢复共同形成的性质。先定义“不应重复的效果”，再讨论系统如何在重试与并发下保持它。
